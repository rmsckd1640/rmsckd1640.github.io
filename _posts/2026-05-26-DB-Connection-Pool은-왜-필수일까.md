DB 연동의 내부 동작 원리를 이해하기 위해 JDBC 기반 외부 데이터베이스를 연동하는 프로젝트를 진행했다.

기능 구현을 마치고 코드를 전체적으로 검토하던 중, DAO에서 매번 `DriverManager.getConnection()`을 호출하여 DB Connection을 새로 생성하고 연결하는 패턴을 발견했다.

혼자 테스트할 때는 문제가 없었지만, 서비스의 규모가 커진다면 이 구조가 치명적인 병목 지점이 될 것을 직감했다.

## 1. DB Connection 연결 과정

DB Connection을 매번 새로 생성하고 호출하는 과정은 내부를 살펴보면 굉장히 무거운 작업이라는 것을 알 수 있다.

>
1. 연결 요청: 애플리케이션에서 `DriverManager.getConnection()`을 호출
>
>
2. 소켓 할당: 운영체제(OS)가 DB와 통신하기 위해 새로운 네트워크 소켓을 생성
>
>
3. 네트워크 확립: TCP 3-Way Handshake 과정을 거쳐 DB 서버와 연결
>
>
4. DB 세션 생성: DB 서버가 계정을 인증하고, 해당 통신을 전담할 스레드와 메모리를 할당한 뒤 Connection 객체를 반환
>
>
5. 쿼리 실행: 만들어진 연결을 통해 SQL을 전송하고 결과를 돌려받음
>
>
6. 종료 요청: 모든 작업이 끝나면 애플리케이션에서 `connection.close()`를 호출
>
>
7. 연결 완전 종료: TCP 4-Way Handshake를 거쳐 네트워크 연결을 완전히 끊고, OS가 소켓 자원을 회수

### 1.1 성능 테스트

이에 대한 성능 영향을 검증하기 위해 성능 테스트를 진행했다.

>**테스트 환경**
>
- 실제 서비스 환경과 유사한 동시 요청 상황을 재현하기 위해 `ExecutorService` 기반 멀티스레드 환경에서 테스트 진행
>
>
- 동시 스레드 수 50개, 스레드당 400회의 요청으로 총 20,000개의 요청을 수행하여, 커넥션 생성 과정의 병목을 관측하기에 충분한 동시성을 유발할 수 있는 수준으로 부하를 설정
>
>
- Warm-up 50회를 선행 수행하여 JVM JIT 컴파일 초기 DB 연결 생성으로 인한 오차 최소화
>
>
- 실행 쿼리는 DB Connection 자체의 성능 비교에 집중하기 위해 `SELECT 1` 사용
>
>
- `System.nanoTime()` 기반으로 요청별 응답 시간을 측정하여 보다 정밀한 성능 데이터 수집
>
>
- p50, p95, p99, TPS, 실패 요청 수를 기준으로 처리 성능 및 안정성 분석 수행
>
>
- MySQL은 별도의 튜닝 없이 기본 설정으로 사용


```java
// 테스트 결과
p50=7.139ms, p95=28.868ms, p99=67.595ms, TPS=525.39 (실패: 1014건)
```

테스트 결과 총 20000개의 요청 중 1014건이 실패하였다.

실패 로그를 분석한 결과 `Communications link failure` 예외가 다수 발생하였으며, 이는 DB와의 TCP 기반 통신 과정에서 연결이 정상적으로 유지되지 못했음을 의미한다.

MySQL에서 `SHOW STATUS LIKE 'Max_used_connections';` 명령어를 통해 동시에 사용된 최대 Connection 수를 확인해 보았을 때, 기본 설정값인 151에 도달하지 않은 68 수준이었다.

이는 단순히 MySQL의 `max_connections` 한계로 인해 장애가 발생한 것이 아니라, 그 이전 단계인 TCP 연결 수립 및 OS 네트워크 처리 과정에서 병목이 발생했을 가능성을 의미한다.

>
물론 MySQL 내부에서도 connection 처리 과정이 동시에 다수 발생할 경우 지연에 영향을 줄 수 있다.
>
MySQL은 TCP 연결 수립 이후 인증 및 세션 생성 과정을 수행한다.
>
이러한 내부 처리 또한 동시 요청이 급격히 증가할 경우 추가적인 처리 지연을 유발할 수 있다.


실제 네트워크 흐름을 확인하고자 `tcpdump`를 통해 TCP 패킷 흐름을 관측해보았다.

초기에는 클라이언트의 SYN(`S`) 요청에 대해 서버가 정상적으로 SYN-ACK(`S.`)을 반환하며 TCP handshake가 정상적으로 수행되는 흐름이 반복적으로 관측되었다.

그러나 부하가 증가한 이후 일부 요청에서는 SYN 패킷의 재전송이 발생하였고, 정상적으로 handshake가 완료되지 못한 상태에서 RST(`R`) 패킷으로 종료되는 케이스도 확인되었다.

또한 이미 수립된 일부 연결에서도 RST 응답이 발생하는 흐름이 관측되었다.

이러한 패턴은 짧은 시간 동안의 대량 연결 요청으로 인해 TCP 연결 수립 과정 또는 OS 레벨의 backlog에서 병목이 발생했을 가능성이 높다.

특히 `SYN backlog` 및 `accept queue` 처리 속도가 요청 유입 속도를 따라가지 못할 경우, 연결 실패 또는 지연이 발생할 수 있다.

"연결을 끊는 과정에서 발생하는 TIME_WAIT 때문일 가능성도 있지 않을까?" 하는 생각에  
`netstat -an | grep 3306 | grep TIME_WAIT | wc -l` 명령어를 통해 TIME_WAIT 개수를 확인해 보았고, 최대 약 16000개 정도 확인하였다.

다만 ephemeral port 고갈 수준(`Cannot assign requested address` 오류 발생 조건)까지는 도달하지 않은 것으로 보이며, 해당 문제로 단정하기에는 근거가 부족하였다.

따라서 포트 고갈보다는 connection 생성/해제 반복으로 인한 TCP 레벨 부담 증가가 더 주요한 요인으로 판단된다.

결과적으로 본 문제는 짧은 시간 동안 반복적으로 발생한 connection 생성/해제 과정에서 TCP 및 OS 레벨의 연결 처리 부하가 집중되면서 발생한 연결 안정성 저하로 판단된다.

## 2. DB Connection Pool 적용

매 요청마다 반복적으로 발생하는 connection 생성/종료 비용을 줄이기 위해, 미리 생성된 connection을 재사용하는 커넥션 풀(Connection Pool)을 적용하여 구조 개선을 진행하였다.

>**Connection Pool**
>
매 요청마다 새로운 DB 연결을 생성/종료하지 않고, 미리 만들어둔 Connection을 빌려 쓰고 반납하여 성능과 자원 효율을 개선하는 방식이다.
>
**Connection Pool 적용 시 연결 과정**
>
1. 연결 요청: 애플리케이션에서 커넥션 풀에 `getConnection()` 요청
>
>
2. 커넥션 즉시 획득: 풀에 대기 중인 커넥션을 가져옴
>
>
3. 쿼리 실행: 획득한 커넥션의 세션을 통해 SQL을 전송하고 결과를 돌려받음
>
>
4. 종료 요청: 모든 작업이 끝나면 애플리케이션에서 `connection.close()`를 호출
>
>
5. 풀에 반납: TCP 4-Way Handshake를 하지 않고 네트워크와 DB 세션을 그대로 살려둔 채, 커넥션의 상태만 '대기(idle)'로 바꿔 풀에 반납

커넥션 풀은 다양한 라이브러리(Tomcat DBCP, C3P0 등)가 있지만, 성능 오버헤드가 가장 작고 검증된 안정성으로 널리 알려진 HikariCP를 사용하였다.

커넥션 풀 사이즈는 [HikariCP](https://github.com/brettwooldridge/hikaricp) 및 [PostgreSQL](https://wiki.postgresql.org/wiki/Number_Of_Database_Connections) 공식 가이드에 따라  
`((core_count * 2) + effective_spindle_count)`을 바탕으로 16개로 초기값을 설정했으며, 향후 필요시 시스템 상황에 맞춰 튜닝할 계획이었다.

>**커넥션 풀 사이즈를 많이 키운다고 무조건 좋은 것이 아니다.**
>
- 컨텍스트 스위칭(Context Switching) 낭비
>
한정된 CPU 코어에서 너무 많은 스레드를 번갈아 실행하느라, 정작 데이터 처리보다 스레드 상태를 교체하는 데 CPU 자원을 다 써버린다.
>
- 물리적 디스크 I/O 한계
>
데이터베이스 작업은 결국 디스크에서 데이터를 읽고 쓰는 것이다. 디스크의 물리적 처리 속도는 한정되어 있어, 커넥션만 늘려봤자 대기 줄만 길어지고 병목 현상만 심해진다.
>
- 락(Lock) 경합 폭발
>
너무 많은 커넥션이 동시에 같은 테이블이나 데이터에 접근하면서 내부적인 트랜잭션 충돌과 락 대기가 기하급수적으로 증가한다.


[HikariCP 공식 문서](https://github.com/brettwooldridge/HikariCP)의 권장 사항에 따라, 트래픽 스파이크 상황에서의 응답성과 최대 성능을 확보하기 위해 minimumIdle 값을 따로 설정하지 않고 고정 크기 풀로 구성했다.

>_"for maximum performance and responsiveness to spike demands, we recommend not setting this value and instead allowing HikariCP to act as a fixed size connection pool."_

### 2.2 성능 테스트

커넥션 풀을 적용했을 때 성능 개선이 얼마나 되는지 확인해보자.

```java
// 테스트 결과
p50=0.234ms, p95=3.902ms, p99=22.718ms, TPS=40937.49 (실패: 0건)
```

| 항목    | Connection Pool 적용 전 | Connection Pool 적용 후 |          개선 효과 |
| ----- | -------------------: | -------------------: | -------------: |
| P50   |              7.139ms |              0.234ms |   96.7% 감소 |
| P95   |             28.868ms |              3.902ms |   86.5% 감소 |
| P99   |             67.595ms |             22.718ms |   66.4% 감소 |
| TPS   |               525.39 |            40,937.49 | 약 77.9배 증가 |
| 실패 건수 |               1,014건 |                   0건 |    100% 제거 |


Connection Pool 적용 후 응답 시간이 전반적으로 감소하고 TPS가 약 78배 향상되었으며, 기존 테스트에서 발생하던 1,014건의 실패 요청 또한 모두 제거되었다.

이는 매 요청마다 반복적으로 발생하던 TCP 연결 생성 및 종료 과정이 제거되었기 때문이다.

## 3. 결론

기존 구조에서는 요청마다 새로운 connection을 생성하면서 TCP handshake, DB 인증 및 세션 생성, 연결 종료 과정이 반복적으로 발생하였고, 이로 인해 네트워크 및 OS 레벨에 큰 부하가 집중되었다.

반면 커넥션 풀 적용 이후에는 미리 생성된 connection을 재사용하게 되면서 이러한 오버헤드가 대부분 제거되었고, 결과적으로 처리 성능과 연결 안정성이 모두 크게 향상되었다.
